# PLSI v0.2.1 -> v0.3.0

Moving a Grok Bot PLSI install to v0.3.0 without losing instance `me`, the research or the patients: one
orchestrator becomes up to three hubs (Health, Research, Clinic) plus a Ward bot per patient on request, the two research bots
go, session rooms replace the expert room, and the shared team moves from memory to `<PLSI_HOME>/team.json`. The
primary hub reads this file from `plsi.md` step 2 when it finds an install set up with v0.2.1; an operator can follow
it by hand too. An older install applies `migration/v0.2.0.md` and `migration/v0.2.1.md` first, then this one.

The steps below run inside the normal `plsi.md` run, each at the step named; they never replace one. From the
update check, run only the `plsi.md` steps named below, in this order: no welcome and no setup cards except those
named here. Personal, researcher and physician installs share them; the role-specific parts are marked.

## What is new

- **Hubs:** the bots the user talks to, each in its own chat and for its own use case: PLSI · Health Orchestrator
  (own health and family), PLSI · Research Orchestrator (research), PLSI · Clinic Orchestrator (a physician's panel)
  and a Ward bot for each patient the physician opens one for (section **Ward**, made on request). The workers are shared and reply to the hub that sent the
  request; work outside a hub's use case goes hub to hub (`orchestrator/answer`).
- **The primary hub:** the bot that ran `plsi.md`. It creates the other hubs and runs the update check, "PLSI
  feedback", "PLSI Mothership replies" and the persona rollout.
- **`plsi team`** (`show`, `set`, `add`, `remove`): the team, the primary hub, own health, the Terms accepted, the
  PLSI version and the PLSI Sessions answer in `<PLSI_HOME>/team.json`, the same for every hub.
- **Research on the Research Orchestrator:** it runs sessions (`lab/session`) and the daily loop (`lab/run` and the
  moves `lab/ask`, `gather`, `explain`, `test`) itself; `orchestrator/research` is now `lab/research`.
- **Research projects** (`plsi research project`): all research lives in projects, `research/projects/<project>/`
  with its topics, notes and data; several can be open at once, each with its room and its daily routine; notes of
  a project link to each other; the Mothership groups a note by its project.
- **Session rooms** (`shared/sessions`): one group chat per task, up to 6 bots, which the user drags into the section **PLSI Sessions** (a bot cannot place a group chat);
  the weekly Mothership send ("Mothership sync") and target discovery run in one.
- **Ward bots** (physician, `clinic/ward`): the physician works on one patient in that patient's own bot.
- **The PLSI version in every Mothership file** (`plsi_version`: research notes, feedback reports, registry
  updates, contributions), so the PLSI team never chases a bug a newer version already fixed. The consent marker
  is now `0.8.0`: a joined install gets `CONSENT_OUTDATED` at its next weekly send and shows the kinds card again
  with `mothership/consent.md` (`orchestrator/mothership`, re-consent); the send mode stays.
- **Research note tags:** 1-5 MeSH descriptors per item (`plsi mesh find`), with the hallmarks of aging, in place of
  the old four-value `topic`.
- **Persona 2.8.0:** the hubs, and "PLSI" in every skill means the hub that sent the request.

## What is gone

- **PLSI · Citizen Researcher and PLSI · Research Autopilot** as bots. Their notes, topics, cursors and budget stay
  under `PLSI_HOME`; the Research Orchestrator works them. Bots are deleted only by the user, in Grok.
- **"PLSI · Chief Orchestrator"** as a name and title (step 3 below).
- **The PLSI expert room.** Rooms are per task now, in PLSI Sessions.
- **The team, own health, "Terms accepted" and "PLSI version" in the orchestrator's memory.** `plsi team show` is
  the source; memory is not read for them any more.
- **The panel line in "PLSI check-in"** (physician): the Clinic Orchestrator's weekly "PLSI panel overview" takes it.

## What stays

- Instance `me`, every other instance and the patients' roster (`work/panel/roster.json`).
- Every worker and section bot, its Display name and its old chats: updated in place, never recreated.
- Research topics and notes, moved unchanged into one project, **Earlier research** (step 5, `plsi research
  project --adopt`); the active topic keeps its status; the budget and the targets stay where they are. New research
  starts its own projects.
- Recorded lab results. Codes picked automatically before v0.3.0 may be wrong for some tests (Total cholesterol
  coded as LDL, a urine result as a blood one); v0.3.0 checks every new result, and a wrong old one is corrected
  with `processor/intake` (Correct) when the user notices it.
- Keys, connectors, the Mothership join, its install token and the professional token.
- The Terms (marker unchanged): no Terms card, only the marker copied into `team.json`.

## Steps

1. **Install** (`plsi.md` step 1): `git -C <repo> fetch --tags`, `git -C <repo> checkout v0.3.0`, then
   `python -m pip install -e <repo>`. `plsi --version` says `plsi 0.3.0`. An install that runs the update check does
   this when the user taps Update. The Terms check reads the remembered "Terms accepted" this once (no `team.json`
   yet); the marker is unchanged, so no card.
2. **The team file** (`plsi.md` step 2), from your memory, before anything else is created. The primary hub is you,
   the old orchestrator, with the slug your role gives it (step 3): `orchestrator` for an individual, `lab` for a
   researcher, `clinic` for a physician.

   ```bash
   plsi team set --primary <orchestrator|lab|clinic> --own-health <on|off> --terms <remembered marker>
   plsi team add --role <your slug> --display-name "<your name after step 3>"
   plsi team add --role <slug> --display-name "<name>" --hub <your slug>     # once per remembered bot
   ```

   An individual is own health on. A researcher or physician whose memory and `plsi team show` hold no own-health
   answer (installs
   before v0.3.0 often have none, and none is not "off") gets the `plsi.md` step 6.3 card "Use PLSI for your own
   health too?" first, as the only question of this step, and its answer goes into `--own-health`. Skip Citizen
   Researcher and Research Autopilot. Then stop reading the team from
   memory.
3. **Your identity** (`plsi.md` step 3). Decided by role, so a fresh install and a migrated one look the same:
   - individual: rename yourself to PLSI · Health Orchestrator (title Health Orchestrator, red star);
   - researcher: you become PLSI · Research Orchestrator (the `lab` row, blue star); your skills are now
     `skills/lab/` plus the hub skills;
   - physician: you become PLSI · Clinic Orchestrator (the `clinic` row, green star); your skills are now
     `skills/clinic/` plus the hub skills.
   Keep a custom name. Remember the new slug and skills (`plsi.md` step 4.3).
4. **Workers** (`plsi.md` step 5). Every worker's, specialist's and section bot's description and first message changed (handoffs from the PLSI
   hubs, replies to the hub that sent the request): update the description and send the complete first message
   once, on thread `setup-v0.3.0`.
5. **The research bots** (`plsi.md` step 7). Close their open threads (`orchestrator/conduct`), delete the routines
   that send them requests, and ask the user in one line to delete PLSI · Citizen Researcher and PLSI · Research
   Autopilot in Grok ("their research stays; PLSI · Research Orchestrator carries it on").
   Their notes now name their kind as on the wire: in each file of `<PLSI_HOME>/research/notes/` whose frontmatter
   says `kind: note`, change only that line to `kind: plsi_research_note` (the one hand edit of this step; if adopt
   already ran, make the same edit in `research/projects/*/notes/`, and take the names for `research check` from
   adopt's `moved_notes`). Then
   move all research into projects, and check every note:

   ```bash
   plsi research project --adopt        # topics and notes into "Earlier research"; run again, it moves nothing twice
   plsi research check --name <note> --project "Earlier research"
   ```

   An `ADOPT_SKIPPED` warning (a name already taken) and a note that still has violations are listed for the
   Research Orchestrator in its hand-over below; nothing else in a note changes.
6. **The other hubs** (`plsi.md` step 7), each with its first message and `plsi team add`:
   - PLSI · Health Orchestrator when own health is on and you are not it;
   - PLSI · Research Orchestrator when you are not it and research was on: Citizen Researcher or Research Autopilot
     was on the team, the routine "PLSI research" exists, or `plsi research topic` lists a topic.
   Hand each its part in ONE hub-to-hub `request` (skill `shared/team`, thread `setup-v0.3.0`): its routines (step
   8), the user's standing answers they need ("oracle consent: <never|ask each time|always>; Mothership send mode:
   <mode>; standing approvals: <list>", from your memory; a hub with no recorded answer asks the user before any
   oracle ask or Mothership send) and, for the Research Orchestrator, the "Sent target file …" and "Receipt r_…"
   lines from your memory, so it can match the Mothership's replies.
7. **Sessions** (`shared/sessions`, The section). The "PLSI expert room" is not used again; the user may delete it.
   A section the user made for rooms ("Research Sessions"): ask in one line to rename it PLSI Sessions. When PLSI
   Sessions exists, `plsi team set --sessions-section ready`; otherwise the first room asks.
8. **Routines** (`plsi.md` steps 10-12 and 15). A routine runs on the bot that created it, so a routine that moves
   is deleted here and created on its new hub:
   - "PLSI research": deleted, and on the Research Orchestrator "PLSI research · Earlier research" (its room opened
     as `shared/sessions` says) and the weekly "PLSI research check" are created (`lab/research`, Daily research);
     the budget and the active topic stay. With no active topic (`plsi research topic`), the Research Orchestrator
     runs `lab/research` Daily research step 1 in its own chat right after: `plsi research propose`, then `plsi research
     discover --about "<subject>"`, then the ONE
     card "What should your daily research work on?". A routine left with no topic does nothing;
   - "PLSI check-in" (without the panel line), "PLSI talk", "PLSI longevity digest" and "PLSI Mothership": on the
     Health Orchestrator (the digest stays on you when own health is off);
   - "PLSI update check", "PLSI feedback" and "PLSI Mothership replies": stay on you, the primary; save "PLSI update
     check" again with the text and schedule of `plsi.md` step 10 (Monday and Thursday, 09:00). A routine keeps
     the instructions it was saved with, so update "PLSI Mothership replies", if it exists, now to `shared/hub` (Mothership
     replies) as it reads today: a reply about a research note or a target file is handed to the Research
     Orchestrator hub to hub and nothing is said of it in your own chat; only the Research Orchestrator sets the
     note's status, from a decision that quotes its kept receipt. Then read the Mother's emails already in the
     inbox once, as that section says, and hand over any decision on a `submitted` note that has not been marked;
   - own health off (no Health Orchestrator): delete "PLSI check-in" and "PLSI talk"; the digest stays on you, and
     "PLSI Mothership" exists only if the user's own instance joined.
   An individual moves only the research routines, and still saves "PLSI update check" and "PLSI Mothership
   replies" again as above.
9. **Open Wearables** (only with PLSI Wearables and Open Wearables connected): a `request` to Wearables,
   `wearables/open-wearables` step 9. A key the earlier setup made or kept in a file (a `secrets` folder, setup
   notes) is rotated by the user and added with the secret card; a server on this computer whose admin password the
   user never chose gets a sign-in the user chooses (its step 2), set on the server once from the old one (its step
   9; a new install only on the user's yes), and its start at boot is removed (it now runs only
   for syncs). Nothing found: nothing changes.
10. **Persona** (`plsi.md` step 4): adopt 2.8.0 when the user taps Adopt and send it to every other bot in `plsi team show`,
   the new hubs and Ward bots included.
11. **Version** (`plsi.md` step 14): `plsi team set --version 0.3.0`.
12. **Smoke check** (before `plsi.md` step 14), below.

## Physician installs

- You are the Clinic Orchestrator (step 3); `plsi role show` reads `physician`.
- Rename the `+patients` routine to **"PLSI patient mail"** and save it again with the text of `clinic/panel`
  step 2; never a second trigger on that address.
- A daily clinic sync routine the physician had: rename it **"PLSI clinic sync"** and save it again with
  `clinic/panel` step 4; none: create none.
- Create the ENABLED weekly **"PLSI panel overview"** (`clinic/panel` step 5).
- **Ward bots** (`clinic/ward`): none are made here; each is opened on request, when the physician first works on
  that patient (a Grok account holds at most 50 bots). An open thread about one patient stays with you until the
  physician picks it up, which opens that patient's Ward bot and hands the thread over as a hub-to-hub `request`.
- Own health on: the Health Orchestrator (step 6) takes the check-in, talk, digest and Mothership routines.
- Smoke check: PLSI Clinic populated, no Ward bots yet in `plsi team show`, no Lab bots.

# PLSI v0.3.0 -> v0.3.1

A patch release: fixes from the first v0.3.0 upgrades. No bot, instance, routine name or persona changes.

## What changes

- **Insulin in pmol/L.** `cardiometabolic` 1.3.2 converts fasting insulin from pmol/L (1 µIU/mL = 6.00 pmol/L,
  Knopp et al. 2019), so a UK report in pmol/L projects insulin and HOMA-IR again.
- **Local edits no longer block updates.** The update check offers a release over local edits: they are stashed,
  re-applied after the checkout, and named when the release already has them or when they conflict
  (`plsi.md` step 10).
- **Open Wearables** (`wearables/open-wearables`): the backend env file is named for both setups (`deploy/.env`,
  `backend/config/.env`); the test read finds the URL and key where `plsi keys status` does; the API key goes in
  `X-Open-Wearables-API-Key`, not the `Authorization: Bearer` the portal suggests; step 9 changes an install-time
  admin email as well as the password, and sends `confirm_password`; **Docker running** reuses a daemon started
  with sudo instead of starting a second one.

## Steps

1. **Code** (step 2, after the update): `plsi --version` says `plsi 0.3.1`; `plsi maps show cardiometabolic` says
   `map_version` 1.3.2.
2. **A local insulin edit.** An install that added the pmol/L conversion to `maps/cardiometabolic.yaml` by hand has
   it from the release now: after the update `git -C <repo> status --porcelain` no longer lists the file. Still
   listed: `git -C <repo> diff maps/cardiometabolic.yaml`, and when it differs only in that conversion,
   `git -C <repo> checkout -- maps/cardiometabolic.yaml`.
3. **Insulin projected again.** Nothing to re-ingest: an insulin observation already recorded in pmol/L projects
   with the new conversion; `plsi state show --instance <instance> --map cardiometabolic` shows fasting insulin and
   HOMA-IR.
4. **Routine** (step 10): save "PLSI update check" again with the text of `plsi.md` step 10, schedule unchanged
   (a routine keeps the text it was saved with).
5. **Open Wearables on this computer, set up before 0.3.1:** when `plsi keys status` shows
   `OPEN_WEARABLES_ADMIN_EMAIL` set and the account still signs in with the install-time `admin@…` email, run
   `wearables/open-wearables` step 9 once. Nothing to do for a server elsewhere.

An install on 0.3.0 with local edits is not offered 0.3.1 by its old update check: the user says "update PLSI",
and you follow step 10 as it reads in the release (`git -C <repo> show v0.3.1:plsi.md`).

## Smoke check

```bash
git -C <repo> describe --tags          # v0.3.1
plsi --version                         # plsi 0.3.1
plsi maps show cardiometabolic         # map_version 1.3.2
```

# PLSI v0.3.1 -> v0.3.2

A patch release: two fixes. No bot, instance, routine or persona changes.

## What changes

- **Values that give the age back stay on this computer.** A value in years (a lab-reported clock or organ age, an
  age difference), a value derived from the age, and any coordinate a map marks `local_only: true` never go to the
  Mothership or into a PandaOmics Agent prompt. Until now a measured clock age from a user map was sent, and oracle
  prompts carried PhenoAge and chronological age. `womens_health` 0.2.0 marks `months_since_final_period` local
  and age at menarche and at menopause shareable. A user map may mark a coordinate `local_only: true`, never
  `false`.
- **Methylation arrays from Illumina MSA and EPICv2.** Replicate probe suffixes (`cg00000029_BC11`) are stripped
  and the replicates averaged before the clocks run, so the clocks read these arrays; files already imported are
  read correctly at the next projection.

## Steps

1. **Code** (step 2, after the update): `plsi --version` says `plsi 0.3.2`.
2. **Clocks again.** An instance with a methylation file from an MSA or EPICv2 array: `plsi project --instance
   <instance> --map methylation_clocks`; clocks that failed or were missing now have values.
3. **A user map with values that encode age** (a percentile for age, a pace of aging): add `local_only: true` to
   those coordinates and install the map again (`processor/add-map`). Values in years need nothing.
4. **Contributions held back.** An install that paused Mothership contributions because Data Controller refused a
   package with an age in it may resume them: the next package (`plsi mothership pack --instance <instance>`)
   leaves those values out, and Data Controller checks it as before.

## Smoke check

```bash

plsi maps show womens_health           # map_version 0.2.0
```
